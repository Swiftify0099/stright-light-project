## 2. Protocol Compatibility, Security & Safety Risks

1. **Protocol Compatibility Risk:** Upgrading `MeshPacketHeader` from 16 bytes (`v0x01`) to 22 bytes (`v0x02`) breaks wire compatibility with `v0x01` nodes by design; `v0x01` frames are explicitly rejected (`packetsDroppedMalformed`) rather than misparsed. Total max wire frame = `22 + 128 + 2 = 152` bytes (SX1278 FIFO = 256 bytes; ~45 ms additional SF10 airtime over `v0x01`).
2. **Symmetric PSK Limitation on Hop Identity:** Current MSCB security architecture provisions one shared 256-bit PSK (`MSCB_PROVISIONED_AES_KEY`) across Gateway and Field Poles. Therefore `hopAuthToken` (32-bit HMAC-SHA256) prevents unauthenticated/outsider spoofing and mutable routing-header tampering fail-closed, **but cannot cryptographically prevent a compromised insider node that already holds the shared PSK from impersonating another node's `previousHopAddress`**. Full insider non-repudiation would require per-node pairwise keys or hardware ECDSA signatures, which is documented as an architectural boundary.
3. **Electrical Safety & Mains Isolation:** No 230V/415V testing is permitted. Discrete relay board lacks an ESP32-controlled hardware enable/interlock kill line; hardware emergency interruption remains `NOT IMPLEMENTED`, and production builds maintain `MSCB_RELAYS_LOCKED_DISABLED = 1`.
4. **TLS Certificate Maintenance Risk:** `api.telegram.org` currently presents a leaf cert issued under `Go Daddy Root Certificate Authority - G2` (valid to Dec 31, 2037). Trust store includes GoDaddy G2, DigiCert Global Root CA / G2, and ISRG Root X1; certificate bundle renewal is required if Telegram rotates to an unlisted CA before firmware OTA update.

   - **Section Y:** Rank overflow (`254/255`), equal/higher rank rejection, `myRank` rules, `maxHops=0`/`>6`, `hopCount >= maxHops`, invalid `nextHop`, parent-child cycle & transitive descendant rejection, orphan reachability, backup failover rank.
   - **Section Z:** Authenticated `previousHopAddress`, grandchild exclusion, spoofed `hopAuthToken` rejection, broadcast non-registration, duplicate/stale sequence replay rejection, `ONLINE -> SUSPECTED -> OFFLINE -> RECOVERED -> ONLINE` lifecycle, full table protection, multi-hop `Child -> Parent -> Intermediate -> Gateway -> Alert Queue` propagation.
   - **Section AA:** Full-queue pending retention, retry drain on pop, deduplication, recovery preservation, cooldown + retry interaction, Telegram delivery failure not marking delivered.
   - **Section AB:** LVDC commissioning compile-time & runtime requirements, reboot clears auth, expired auth blocks switching, emergency shutdown overrides normal operation (plus dedicated `test_r3_2_2_production_lock.cpp` proving production build `MSCB_RELAYS_LOCKED_DISABLED=1` cannot be bypassed by ANY setter, remote command, or Telegram).

   - **Section AD:** Complete 16-pin + 21-channel ADC config validation, corrupt CRC/schema/duplicate/input-only/collision/invalid-ADC-map rejection, zero partial apply, factory fallback, drivers consuming applied pins.
   - **Section AE:** Sender `fromUserId` vs `chatId` enforcement, group participant rejection, spoofed chat ID rejection, malformed callback rejection, TLS cert & time-sync failure blocking requests.
   - **Section AF:** Truthful metrology report (`-NAN-`, `SENSOR_UNAVAILABLE`, `NOT_CALIBRATED`, `INVALID_READING`, `OUT_OF_RANGE`, `STALE`, `VALID`), ADS131M08 ID/STATUS checks, host staleness transition.

4. **Firmware Builds & CI:** Clean `arduino-cli` builds for `esp32:esp32:esp32s3` (Gateway) and `esp32:esp32:esp32` (Field Pole), zero modifications to `main`, `Sender/`, `Resivers/`, and passing GitHub Actions `.github/workflows/r3-2-2-verification.yml`.
